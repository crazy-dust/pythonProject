## 2.1 Python 与 Java 的思维迁移

### 2.1.1 Python 基础数据类型

状态：【已动手并通过评审】

一句话解释：

Python 可以直接使用 dict、list、str、int 等类型组织业务数据，不需要像 Java 一样为每个简单数据结构定义类。

Java 对照：

| Python | Java 类比 |
|---|---|
| dict | HashMap |
| list | ArrayList |
| tuple | 不可变序列的近似概念 |
| None | null |
| def | 方法或函数定义 |
| raise | throw |
| except | catch |

原理：

Python 是动态类型语言。

变量保存的是对象引用，变量本身不需要像 Java 局部变量那样显式声明静态类型。

例如：

```python
order = {
    "order_id": "SO-1001",
    "status": "PAID"
}
```

可以直接处理 JSON 风格的数据。

常见误区：

认为 Python 不需要类型校验。

实际上，动态类型只是让编程更灵活，不意味着外部数据可靠。

生产注意：

第三方 OMS、WMS、ERP 接口返回的 JSON 必须经过字段、类型和业务规则校验。

举一反三：

查询 Shopify 订单时，可以先解析 JSON 为 dict，再转换成内部统一的订单对象。

### 2.1.2 dict.get()、None 与字段缺失

状态：【已动手并通过评审】

一句话解释：

dict.get() 可以安全地读取字典中的字段，但无法自动区分字段不存在与字段存在且值为 None。

Java 类比：

类似 Map.get()，但仍然需要判断业务字段的合法性。

原理：

```python
order.get("wms_status")
```

字段不存在时，默认返回 None。

如果字段存在，但值就是 None，同样返回 None。

因此：

```python
"wms_status" not in order
```

和：

```python
order.get("wms_status") is None
```

判断的不是完全相同的问题。

常见误区：

```python
if not order.get("wms_status"):
    ...
```

这不仅会匹配 None，还会匹配空字符串、0、False 等假值。

生产注意：

至少区分：

1. 字段不存在。
2. 字段存在但为 null。
3. 字段存在但类型不正确。
4. 字段存在但业务值不合法。

举一反三：

海外仓库存接口的 available_qty 为 0，可能是合法库存状态，不能简单判定为数据缺失。

---

### 2.1.3 Guard Clause：卫语句与早返回

状态：【已动手并通过评审】

一句话解释：

在进入核心业务逻辑前，先处理不满足条件的情况。

Java 类比：

类似 Java Service 方法中的参数校验和提前 return。

原理：

通过前置条件判断，避免多层 if/else 嵌套。

例如：

```python
if status is None:
    return {
        "result": "数据异常"
    }
```

业务主体只负责处理通过校验的数据。

常见误区：

过早返回一个默认正常结果，可能掩盖未知业务状态。

生产注意：

不能将所有未命中的状态统一归类为正常。

在订单履约场景中：

- CREATED：已知状态。
- NOT_CREATED：已知状态。
- UNKNOWN：如果契约不支持，应标记数据异常。

### 2.1.4 Python 函数参数机制

状态：【已讲解但我未动手】

本会话讲解了：

- 位置参数。
- 关键字参数。
- 默认参数。
- *args。
- **kwargs。
- / 位置专用参数。
- * 关键字专用参数。

一句话解释：

Python 允许函数通过位置、名称和参数解包等多种方式接收调用参数。

Java 类比：

*args 接近 Java 的可变参数。

**kwargs 接近动态传入 Map，但 Java 没有完全对应的关键字参数机制。

原理：

函数调用时，解释器将实参与形参进行绑定。

例如：

```python
def query_order(order_id, *, warehouse="US"):
    pass
```

其中 warehouse 必须通过关键字传入。

常见误区：

认为 **kwargs 越灵活越好。

实际上它会削弱接口契约的明确性。

生产注意：

Agent 工具接口应该尽量定义明确的参数，而不是无限制接收 **kwargs。

这样更容易进行参数校验、权限控制和日志审计。

### 2.1.5 可变默认参数陷阱

状态：【已讲解但我未动手】

曾通过多道题回答其执行机制，但没有提交独立实践代码。

一句话解释：

Python 函数的默认参数通常在函数定义时创建，而不是每次调用时重新创建。

Java 类比：

类似错误地让多个请求共享同一个可变集合实例。

原理：

```python
def add_order(order_id, orders=[]):
    orders.append(order_id)
    return orders
```

多次不传 orders 调用时，会复用同一个默认列表。

原因是默认参数对象被保存在函数对象中。

正确方向：

使用 None 作为默认值，再在函数内部创建新列表。

常见误区：

以为函数每次调用都会自动创建新的默认 list。

生产注意：

Agent 的 messages、tool_calls 和 execution_steps 等可变状态不能意外跨请求共享。

否则可能造成：

- 对话串扰。
- 状态污染。
- 用户数据泄露。

## 2.2 Python 模块、异常与类型系统

### 2.2.1 Module、Package 与 import

状态：【已讲解但我未动手】

一句话解释：

Python 通过模块和包组织代码，import 负责查找、加载并绑定模块。

Java 类比：

近似于 Java package、import 与类加载机制的组合。

但 Python 模块并不等于 Java Class。

原理：

普通 Python 模块第一次导入时，大致经历：

1. 查找模块。
2. 创建模块对象。
3. 将模块放入 sys.modules。
4. 执行模块顶层代码。
5. 完成模块初始化。

再次导入通常会复用已加载模块。

常见误区：

认为 import 只是声明依赖，不会执行代码。

实际上，Python 首次导入模块时会执行模块顶层代码。

生产注意：

不要在模块顶层直接：

- 调用大模型。
- 修改订单。
- 执行数据库写操作。
- 启动批处理任务。

否则单纯 import 就可能产生业务副作用。

### 2.2.2 sys.modules 与循环导入

状态：【讲过但有错误或遗漏】

本会话中曾经判断错循环导入的输出顺序，之后完成纠正。

一句话解释：

sys.modules 是 Python 已加载模块的缓存；循环导入可能访问尚未初始化完成的模块。

Java 类比：

可以借助 Java 类加载和 Spring Bean 循环依赖理解，但实现机制不同。

原理：

假设：

A 导入 B。
B 又导入 A。

此时 A 可能已经存在于 sys.modules 中，但 A 的顶层代码还没执行完。

如果 B 访问 A 中尚未定义的成员，就可能报错。

关键结论：

模块对象存在，不代表模块初始化完成。

常见误区：

认为只要模块已经进入缓存，任何成员都可以正常使用。

生产注意：

推荐保持清晰的依赖方向：

main → services → clients/models

避免 services 之间不必要的双向依赖。

补充：

模块首次导入时发生执行异常，失败模块通常会从 sys.modules 中移除。

### 2.2.3 Python 异常处理

状态：【已动手并通过评审】

但第一次提交的 JSON 解析代码存在 finally 使用错误。

一句话解释：

try/except/else/finally 用于区分正常执行、异常处理和资源收尾。

Java 类比：

try/catch/finally。

Python 多了可直接使用的 else 分支。

执行规则：

正常完成 try：

try → else → finally

发生异常并被捕获：

try → except → finally

异常未被捕获：

try → finally → 异常继续传播

常见误区：

认为 return 后面的普通语句仍会执行。

实际上 return 会结束当前函数调用。

生产注意：

HTTP 流、文件句柄、数据库连接等资源需要明确的清理机制。

不要使用：

```python
except Exception:
    return "正常"
```

这会把真实系统故障伪装成业务成功。

### 2.2.6 TypedDict、NotRequired 与 None

状态：【讲过但有错误或遗漏】

本会话中曾将 NotRequired[str] 误认为可以接受 None，之后纠正。

一句话解释：

核心区别：

```python
wms_status: str
```

必填，不允许 None。

```python
wms_status: str | None
```

必填，允许 None。

```python
wms_status: NotRequired[str]

wms_status: NotRequired[str | None]

生产注意：

## 2.4 Token、上下文窗口与 Temperature

### 2.4.1 Token 是什么？

状态：【已讲解但我未动手】

一句话解释：

Token 是模型处理文本时使用的编码单位，不等于字符、字节或单词。

Java 类比：

不能直接用 String.length() 计算模型 Token 数量。

原理：

Tokenizer 将文本拆成模型能够处理的 Token 序列。

不同模型可能使用不同的 Tokenizer。

因此同一句文本在不同模型上的 Token 数量可能不同。

常见误区：

认为中文一个字就是一个 Token。

或者认为英文一个单词就是一个 Token。

生产注意：

不能只依靠字符串长度预测模型成本。

应优先使用模型 API 返回的真实 usage。

【需核对官方文档】

- 模型对应的 Tokenizer。
- Token 计费规则。
- 缓存输入与普通输入的计费差异。

### 2.4.2 Token 用量与成本统计

状态：【已讲解但我未动手】

一句话解释：

模型调用通常按输入、输出等不同 Token 类别统计使用量，并据此计算费用。

原理：

常见用量字段：

- prompt_tokens：输入用量。
- completion_tokens：输出用量。
- total_tokens：总用量。

部分模型或服务商可能提供更细的用量统计。

成本估算思想：

输入成本 = 输入 Token 数量 × 输入单价

输出成本 = 输出 Token 数量 × 输出单价

总成本还可能受到缓存、推理 Token 和其他计费规则影响。

常见误区：

认为总 Token 数量相同，费用必然相同。

生产注意：

成本统计应绑定：

- run_id
- model
- provider
- prompt_tokens
- completion_tokens
- latency
- cost

所有具体单价和特殊计费规则。

### 2.4.6 Temperature

状态：【已讲解但我未动手】

本会话完成了概率采样解释和架构问答，没有实际参数对比实验。

一句话解释：

Temperature 调整模型生成下一个 Token 时的采样概率分布。

原理：

模型先计算候选 Token 的分数 Logits。

随后通过概率分布和采样策略决定输出。

本会话介绍的简化公式：

P(i) = exp(z_i / T) / Σ exp(z_j / T)

其中：

- z_i：候选 Token 的分数。
- T：Temperature。
- P(i)：调整后的采样概率。

通常：

较低 Temperature：
概率更集中，输出趋向稳定。

较高 Temperature：
候选分布相对平坦，输出趋向多样化。

常见误区：

Temperature = 0 就代表绝对确定性。

实际上不保证每次输出一致，也不保证事实正确。

生产注意：

订单诊断等事实性任务应优先采用稳定性较高的配置，并通过权威数据和业务规则校验结果。

不能把 Temperature 当成幻觉防护措施。

【需核对官方文档】

各模型是否支持 Temperature、允许范围和实际行为。

## 2.5 流式输出、SSE 与 Generator

### 2.5.1 普通响应与流式响应

状态：【已动手并通过评审】

原理：

chunk.choices[0].delta.content
```

message 表示完整消息。

delta 表示增量内容。

常见误区：

认为一个 chunk 一定对应一个 Token。

实际上数据片段与 Token 并不是一一对应关系。

生产注意：

必须识别正常结束、网络中断和异常终止。

不能把不完整的流式文本当作最终业务结论。

### 2.5.2 SSE

状态：【已动手并通过评审】

注：

已使用 SDK 消费流式结果，但没有独立手写 SSE 协议解析器。

一句话解释：

Server-Sent Events 是服务端通过持续 HTTP 响应向客户端发送事件的机制。

Java 类比：

WebFlux SSE、Flux 数据流。

原理：

SSE 常使用：

Content-Type: text/event-stream

服务端持续发送事件数据。

Chat Completions 的兼容流可能出现：

```text
data: {...}

data: {...}

data: [DONE]
```

SDK 通常负责解析事件，再向应用返回 chunk。

常见误区：

认为 SSE 就是 yield。

两者属于不同层次：

SSE：HTTP 事件传输。

yield：Python 生成器的数据产出机制。

生产注意：

代理、网关、客户端连接都可能影响流式输出。

需要考虑：

- 连接中断。
- 超时。
- 缓冲。
- 资源释放。
- 客户端取消。

### 2.5.3 Generator 与 yield

状态：【讲过但有错误或遗漏】

注：

用户已在 LLMClient.stream 中实际使用 yield，但在生成器执行顺序题中曾出现理解错误，后续完成纠正。

一句话解释：

yield 让函数能够产出一个值、暂停执行，并在下一次迭代时从暂停处继续执行。

Java 类比：

类似解释器自动维护状态的 Iterator。

但普通 Java Iterator 不直接提供暂停整个函数执行现场的能力。

原理：

包含 yield 的普通函数属于生成器函数。

调用生成器函数时创建 Generator 对象。

第一次 next() 才开始执行函数体。

每次遇到 yield：

1. 返回一个值。
2. 保存当前执行位置和局部状态。
3. 暂停。
4. 等待下次 next()。

常见误区：

认为调用生成器函数时立即执行函数体。

另一个误区：

认为每次 next() 都会创建新的生成器。

实际上通常是在消费同一个生成器对象。

生产注意：

Generator 可以用于：

- 模型流式输出。
- 大批量订单处理。
- 分页数据获取。
- 日志读取。
- 按批次写数据库。

但不适合直接替代需要随机访问、反复遍历或全量排序的数据结构。

### 2.5.4 Iterable、Iterator、StopIteration

状态：【已讲解但我未动手】

一句话解释：

Iterable 表示可以被迭代；Iterator 表示可以逐项取值；Generator 是 Iterator 的一种。

Java 类比：

Iterable 与 Iterator。

原理：

iter() 获取迭代器。

next() 获取下一项。

迭代结束时产生 StopIteration。

Python for 循环通常会自动处理正常迭代结束。

常见误区：

认为 list 本身就是 Iterator。

list 是 Iterable，但不是直接通过 next(list) 消费的 Iterator。

生产注意：

迭代器通常只能按当前进度继续消费。

已经耗尽的生成器不会自动从头开始。

### 2.5.5 yield from、send 与 close

状态：【已讲解但我未动手】

一句话解释：

yield from 可以委托迭代；send 可以向暂停的生成器发送值；close 可以请求关闭生成器。

Java 类比：

yield from 有些类似连接多个数据生产过程。

close 接近资源关闭操作。

原理：

yield from：

将另一个可迭代对象产生的值逐项交给当前调用者。

send：

在生成器暂停位置恢复执行，并把值传回生成器。

close：

请求终止生成器，使其有机会执行清理逻辑。

常见误区：

认为调用方停止遍历后，底层 HTTP 连接必然立刻正确释放。

生产注意：

LLM 流式封装应考虑 finally、显式关闭和资源作用域管理。

不能只依赖垃圾回收及时清理资源。

### 2.5.6 异步编程与 Event Loop

状态：【已讲解但我未动手】

一句话解释：

事件循环负责调度异步任务，使一个任务等待 I/O 时，其他任务可以继续推进。

Java 类比：

Netty EventLoop、响应式编程中的事件驱动调度。

原理：

async def 定义协程函数。

await 等待异步操作，并在需要时交还事件循环执行权。

asyncio.gather 可以并发等待多个异步任务。

常见误区：

认为异步等于多线程。

或者认为 async 函数中的所有操作都自动不阻塞。

生产注意：

在事件循环中调用同步阻塞操作，可能阻塞其他协程。

I/O 密集型任务适合考虑异步并发。

CPU 密集型任务不能仅靠 asyncio 获得并行加速。

### 2.5.7 TTFT 与总延迟

状态：【已讲解但我未动手】

一句话解释：

TTFT 反映用户多久看到第一个输出；总延迟反映完整请求多久完成。

Java 类比：

原理：

流式输出通常改善用户的感知等待时间。

但不意味着完整生成过程一定更快。

常见误区：

认为启用 stream=True 就一定降低总耗时。

生产注意：

建议分别记录：

- 请求开始时间。

- 最后一个片段时间。

### 2.5.8 流式中断、事件重放与工作流恢复

状态：【已讲解但我未动手】

一句话解释：

客户端断开、模型流中断和 Agent 任务失败是不同事件，不能统一处理。

本会话讨论了两种方案：

方案 A：

客户端断开后取消生成，释放资源。

方案 B：

Agent 与客户端连接解耦，任务继续执行，客户端重新连接后获取历史和后续事件。

原理：

事件重放：

重新发送已经持久化的历史事件。

工作流恢复：

根据 Checkpoint 恢复未完成的执行步骤。

两者不同。

Java 类比：

异步任务系统 + 状态机持久化 + 事件日志。

本会话讲解的标识包括：

- run_id：一次 Agent 任务。
- node_id：工作流节点。
- attempt_id：节点执行尝试。
- event_id：事件标识。

常见误区：

认为模型已经生成 60% 的文本，就可以从第 61% 的位置继续生成。

多数普通模型流式请求不支持这样的精确恢复方式。

生产注意：

任务是否后台继续，应综合考虑：

- 剩余成本。
- 重新执行成本。
- 业务价值。
- 任务重要性。
- 用户取消意图。
- 资源占用。

用户关闭页面，不一定等于用户明确取消任务。

def check_order(order):
    # 1. 读取 order_id
    order_id = order.get("order_id")

    str_status = ""
    if order.get("status") is None:
        str_status = "数据异常"

import json


def parse_order(order_json):
    try:
        json_result = json.loads(order_json)

    except json.JSONDecodeError as e:
        print(f"JSON解析异常: {e}")
        return None

    else:
        print("JSON解析成功")

        # 校验解析结果的数据类型
        if not isinstance(json_result, dict):
            print("数据结构异常，期望字典")
            return None

        return json_result

    finally:
        print("解析结束")


if __name__ == '__main__':
    valid_json = '{"order_id": "SO-1001", "status": "PAID"}'
    print(parse_order(valid_json))

    invalid_json = '{"order_id": "SO-1001", "status": '
    print(parse_order(invalid_json))

    empty_json = '{}'
    print(parse_order(empty_json))

    list_json = '[]'
    print(parse_order(list_json))

```python
import os
import time
from typing import Iterator

from openai import OpenAI


class LLMClient:
    def __init__(self):
        self.model = os.environ["LLM_MODEL"]

        self.client = OpenAI(
            api_key = os.environ["LLM_API_KEY"],
            base_url = os.environ["LLM_BASE_URL"],
            timeout = 20.0,
            max_retries = 2
        )

    def complete(self, prompt: str) -> str:
        start = time.perf_counter()
        response = self.client.chat.completions.create(
            model = self.model,
            messages = [
                {"role": "user", "content": prompt}
            ],
            stream = False
        )

        elapsed = time.perf_counter() - start
        print(f"latency = {elapsed:.2f}s")
        print(f"usage = {response.usage}")

        return response.choices[0].message.content or ""

    def stream(self, prompt:str) -> Iterator[str]:
        stream = self.client.chat.completions.create(
            model = self.model,
            messages = [
                {"role" : "user", "content": prompt}
            ],
            stream = True
        )

        for chunk in stream:
            if not chunk.choices:
                continue

            content = chunk.choices[0].delta.content

            if content:
                yield content

if __name__ == '__main__':
    llm = LLMClient()

    prompt = "介绍一下大模型"

    print("===非流式===")
    print(llm.complete(prompt))

    print("===流式===")
    for text in llm.stream(prompt):
        print(text, end="", flush=True)
    print()
```

### 4.3.9 stream() 解决什么问题？

```python
def stream(self, prompt:str) -> Iterator[str]:
```

负责：

1. 创建流式模型请求。
2. 逐步消费 SDK 返回的 chunk。
3. 检查 choices 是否为空。
4. 提取 delta.content。
5. 使用 yield 返回文本片段。

数据链路：

模型服务商
↓
HTTP SSE
↓
OpenAI SDK
↓
ChatCompletionChunk
↓
delta.content
↓
yield
↓
业务调用方

关键原理：

yield 是 Python 生成器机制。

SSE 是 HTTP 流式事件机制。

### 5.1.4 流式输出的特殊风险

此时连接中断。

不能直接将这段不完整内容作为最终诊断结果。

应区分：

- RUNNING：仍在执行。
- COMPLETED：完整成功。
- FAILED：执行失败。
- CANCELLED：明确取消。

这些是本周讨论的状态设计方向，并非已经实现的代码。

## 6.3 E03：if not 与 None 判断混淆

## 6.4 E04：异常可能中断整个订单批次

设计异常前先回答：

批量履约任务中的单笔失败隔离。

## 6.13 E13：Generator 执行顺序错误

分类：Python 执行机制。

**现象**

面对：

```python
def test():
    print("A")
    yield 1
    print("B")

g = test()
print("C")
print(next(g))
```

用户最初回答的顺序是：

```text
A
C
B
```

**错在哪**

误认为调用 test() 会立即执行函数体。

**正确做法**

实际输出：

```text
C
A
1
```

解释：

```python
g = test()
```

只创建 Generator 对象。

第一次：

```python
next(g)
```

才执行函数体，打印 A，并通过 yield 产出 1。

**为什么会错**

将普通函数调用语义直接应用到生成器函数。

**怎么避免**

每次分析 Generator 时先区分：

1. 创建 Generator。
2. 开始迭代。
3. 暂停。
4. 恢复。
5. 结束。

状态：【讲过但有错误或遗漏】

后续理解已纠正，但仍保留原错题。

## 6.21 本章复学结论

第一周错误主要分成三类。

**第一类：Python 运行机制与 Java 不同。**

例如：

- Generator 的惰性执行。
- Python 模块初始化。
- TypedDict。
- 可变默认参数。

这类问题需要通过最小代码验证机制。

**第二类：输入校验不够严格。**

例如：

- 未知状态被判断正常。
- if not 与 None 混淆。
- 空字典处理错误。

这类问题需要通过业务契约和边界测试解决。

**第三类：生产级设计需要考虑更多边界。**

例如：

- 流式断开后的恢复。
- 高成本任务是否继续。
- 权威数据的时效。
- Prompt 与后端权限分离。

这类问题不能靠记忆概念解决，需要结合业务约束做架构取舍。

当前最重要的结论：

**第一周的核心问题已经不再是“会不会调用模型”，而是“能否证明模型客户端在异常条件下仍然安全、可观测、可控”。**

## Q01：Python 可变默认参数

### 核心答案

Python 函数的默认参数通常在函数定义时求值。

如果默认值是 list、dict 等可变对象，多次调用可能共享同一个对象。

例如：

```python
def add_order(order_id, orders=[]):
    orders.append(order_id)
    return orders
```

连续调用：

```python
add_order("SO-1001")
add_order("SO-1002")
```

第二次可能得到包含两笔订单的列表。

### 为什么危险？

在 Agent 应用中，如果 messages 使用可变默认列表，不同调用之间可能出现意外共享状态。

风险包括：

- 历史对话污染。
- 跨用户数据串扰。
- 难以复现的逻辑错误。
- 敏感信息泄露。

### 正确做法

使用 None 作为默认值，再在函数内部创建新对象。

```python
def add_order(order_id, orders=None):
    if orders is None:
        orders = []

    orders.append(order_id)
    return orders
```

### Java 类比

相当于多个请求意外共享同一个可变 List 实例。

但 Python 的具体原因是默认参数求值和对象复用机制。

### 面试加分点

除了可变默认参数，还应该检查：

- 全局变量。
- 类变量。
- 单例服务持有的可变状态。
- 多请求之间复用的缓存对象。

## Q02：TypedDict 与 NotRequired

### 核心答案

```python
status: str
```

字段必填，静态类型定义不允许 None。

```python
status: str | None
```

字段必填，但可以为 None。

```python
status: NotRequired[str]
```

字段可以不存在；存在时应为 str。

```python
status: NotRequired[str | None]
```

字段可以不存在；存在时可以为 str 或 None。

### 原理

字段是否必需，与字段是否允许 None，是两个独立维度。

TypedDict 主要用于静态类型检查。

它不会自动校验运行时 JSON。

### Java 类比

类似 DTO 的：

- 字段是否必须存在。
- 字段是否允许 null。

### 生产级补充

外部系统输入仍需要：

1. JSON 解析。
2. 结构校验。
3. 字段类型校验。
4. 业务规则校验。

### 常见误区

把：

```python
NotRequired[str]
```

理解成字段允许 None。

这是第一周曾经出现并已纠正的问题。

## Q03：Token 与上下文窗口

### 核心答案

Token 是模型处理文本的编码单位。

它不等于：

- 字符。
- 字节。
- 英文单词。
- Java String.length()。

模型的上下文窗口限制单次请求能够处理的信息量。

模型请求可能包含：

- System Prompt。
- 用户问题。
- 历史对话。
- 工具返回结果。
- 输出预算。

### 工程原则

不能只根据字符长度判断是否会超限。

应结合模型的 Tokenizer、上下文限制和 API usage。

### 生产级设计

使用 Token Budget Manager：

1. 明确模型上下文容量。
2. 估算输入 Token。
3. 预留输出预算。
4. 保留关键业务事实。
5. 压缩冗余内容。
6. 在发送请求前检查容量。

### 常见误区

直接截取最近 N 个 Token。

这样可能丢失早期重要约束。

### Java 类比

类似有容量限制的缓存预算。

但不能简单使用 LRU，因为信息重要性与时间先后并不完全一致。

## Q04：Temperature 为什么不能保证正确性？

### 核心答案

Temperature 调整模型生成下一个 Token 时的采样概率分布。

较低 Temperature 通常使概率分布更加集中。

较高 Temperature 通常使输出更加多样。

但：

**Temperature=0 不等于模型输出绝对确定，也不等于事实正确。**

### 为什么？

即使模型始终选择概率最高的 Token，也可能：

- 错误理解输入。
- 使用错误的业务推理。
- 忽略重要条件。
- 受到不准确上下文影响。
- 生成与事实不符的结论。

### 订单诊断的正确策略

对于有明确业务规则的问题：

- 查询可信 OMS、ERP、WMS 数据。
- 进行确定性业务校验。
- 使用 LLM 解释和归纳。
- 对高风险操作实施独立授权。

### 面试加分点

多数投票也不能保证正确。

多个模型回答可能具有相关性错误。

## Q05：dict.get() 与库存数量

代码：

```python
def check(data):
    if not data.get("available_qty"):
        return "缺少库存"

    return "库存正常"


print(check({"available_qty": 0}))
print(check({"available_qty": None}))
print(check({}))
```

### 正确输出

```text
缺少库存
缺少库存
缺少库存
```

### 为什么？

因为：

- 0 是假值。
- None 是假值。
- 缺少字段时，get 默认返回 None。

### 业务区别

第一种：

```text
available_qty = 0
```

表示明确返回了零库存。

第二种：

```text
available_qty = None
```

表示字段存在，但没有有效数值。

第三种：

```text
字段不存在
```

表示数据缺失。

这三种情况不应全部解释为同一种业务状态。

### 正确处理方向

先判断字段是否存在。

再判断是否为 None。

最后检查是否为有效数值，并按照库存业务规则判断。

### Java 类比

不能把有效库存数量为 0，与库存字段缺失混为一谈。

## Q06：try/except/else/finally

代码：

```python
def parse():
    try:
        print("A")
        return 100
    except Exception:
        print("B")
    else:
        print("C")
    finally:
        print("D")


print(parse())
```

### 正确输出

```text
A
D
100
```

### 执行原因

1. 进入 try。
2. 输出 A。
3. 执行 return 100。
4. 返回前先执行 finally。
5. 输出 D。
6. 函数返回 100。
7. 外层 print 输出 100。

### 为什么没有 C？

因为 try 中发生了 return。

else 不是只要“没有异常”就无条件执行。

它要求 try 块正常完成，而不是通过 return 提前退出。

### 重要补充

finally 中如果再次 return 或抛出异常，可能改变原本的返回结果或异常传播。

因此不建议随意在 finally 中 return。

## Q07：Generator 执行过程

代码：

```python
def generate():
    print("start")

    value = 10
    yield value

    value += 5
    print("resume")
    yield value

    print("end")


g = generate()

print("created")
print(next(g))
print(next(g))
```

### 正确输出

```text
created
start
10
resume
15
```

### 关键过程

执行：

```python
g = generate()
```

创建 Generator 对象。

但函数体尚未执行。

执行第一次：

```python
next(g)
```

开始执行函数体。

输出 start。

遇到 yield，返回 10 并暂停。

执行第二次：

```python
next(g)
```

从上一次 yield 之后继续。

value 从 10 变成 15。

输出 resume。

再通过 yield 返回 15。

### 第三次 next(g)

执行：

```python
next(g)
```

会先输出：

```text
end
```

然后生成器结束，抛出 StopIteration。

如果调用方没有捕获，程序会出现未处理异常。

### Java 类比

Generator 是保存执行进度和局部状态的 Iterator。

不是每次 next 都创建一个新的 Generator。

## Q10：timeout=20 为什么总耗时超过 20 秒？

### 核心答案

因为 SDK 的 timeout 配置不一定等于整个业务请求的全局截止时间。

可能原因：

1. 单次请求超时后发生自动重试。
2. 重试之间存在退避等待。
3. 不同网络阶段采用不同超时语义。
4. 流式读取可能持续进行。
5. 业务代码外层还存在其他等待操作。

### 排查方法

记录：

- 请求开始时间。
- 每次调用或重试时间。
- 最终完成时间。
- 异常类型。
- 实际发送请求次数。
- SDK 版本。

再核对 SDK 的具体 timeout 和 retry 行为。

### 生产级解决方向

除了单次请求超时，还要设计：

- 总执行截止时间。
- 最大重试预算。
- 最大 Token 预算。
- 明确的取消策略。

### 重要边界

不能直接根据：

```python
timeout=20.0
max_retries=2
```

推断固定的最大总耗时。

【需核对官方文档】

本周没有完成该故障测试。

## Q11：SSE 输出到一半发生中断

### 如何判断是否成功？

不能只看已经收到了多少文本。

需要知道：

- 是否正常结束。
- 是否收到完整结果。
- 是否出现异常。
- 业务结果是否通过校验。

### 如何处理已输出文本？

可以保留为部分输出或失败记录。

但不能直接当作最终业务诊断结论。

### 如何释放资源？

- 停止继续消费。
- 通知相关任务取消或结束。
- 明确关闭底层流式资源。
- 记录失败状态。

具体 SDK 关闭方式需核对官方文档。

### 是否立即重试？

不应无条件重试。

要检查：

- 任务是否已经取消。
- 是否已有部分输出。
- 重新生成是否会造成重复内容。
- 是否超过成本预算。
- 是否存在副作用。

区分：

- 客户端断开。
- 模型请求失败。
- Agent 任务取消。
- 后台任务继续。
- 历史事件重放。

## S02：Generator 输出顺序

### 正确输出

```text
D
A
10
E
B
15
F
C
END
```

### 过程

调用：

```python
g = generate()
```

只创建生成器。

首先输出 D。

第一次 next：

执行函数体，输出 A，yield 10。

外层继续输出 E。

第二次 next：

从上次暂停处继续，输出 B，yield 15。

外层输出 F。

第三次 next：

恢复执行，输出 C。

函数结束，触发 StopIteration。

异常被捕获后输出 END。

### 关键原理

Generator 保存：

- 执行位置。
- 局部变量。
- 当前迭代状态。

但不会因为调用生成器函数而立即执行函数体。

## S03：异常与返回值

第一种：

```python
return 10
```

### 正确输出

```text
start
finally
10
```

原因：

try 中执行 return。

else 不执行。

finally 执行。

最终返回 10。

### 第二种

将 return 改为：

```python
raise ValueError("invalid")
```

### 正确输出

```text
start
error
finally
None
```

原因：

1. try 输出 start。
2. 抛出 ValueError。
3. except 捕获并输出 error。
4. finally 输出 finally。
5. 函数没有显式返回值。
6. 默认返回 None。

### 关键区别

有 return 的 try 与正常执行到块末尾的 try，控制流不同。

## S10：Temperature 与库存诊断

### 第一问：为什么会答错？

Temperature 控制的是采样随机性。

不能保证模型正确理解 ERP 数据，也不能保证生成事实正确的结论。

### 第二问：哪一层校验？

通过业务代码的确定性规则，对模型结论进行校验。

例如：

当业务规则明确规定可用库存不足时，不允许模型将其描述为库存充足。

但真实判断还需要考虑：

- 订单数量。
- 仓库。
- SKU。
- 锁定量。
- 库存快照时间。

### 第三问：ERP 数据是否可信？

检查：

1. 数据来源。
2. 查询时间。
3. 仓库是否一致。
4. SKU 是否一致。
5. 库存口径是否一致。
6. 是否存在同步延迟。

### 第四问：是否增加模型调用次数？

对于存在明确业务事实和确定性规则的问题，通常不应优先通过重复模型调用解决。

多次回答可能增加成本和延迟，却仍然得到相同的错误结论。
